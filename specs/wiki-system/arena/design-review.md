# Independent design review

## Verdict: NEEDS-REVISION

The scope is appropriate for a design deliverable, and the unrun runtime gates are correctly distinguished from implementation evidence. The following are **design blockers**, not demands to complete those gates now.

| Severity | File and heading | Finding and required correction |
|---|---|---|
| Blocker | **ARCHITECTURE.md — Retrieval and evidence; Index lifecycle** | The specified snapshot cannot reliably be searched as written. Recall releases the SQLite read transaction after capturing `R`, then asks for transactional FTS “as of `R`”; an ordinary current-state FTS table may already have changed. Also, a generation promoted after the snapshot can have `G > R` and omit revisions current at `R`. Define how FTS results and an eligible generation are pinned or reconstructed for `R`, including generation retention and concurrent publication. Test publication and promotion between snapshot acquisition and search. |
| Blocker | **ARCHITECTURE.md — Proposal and publication state machine; contract.d.ts — `operation`** | Idempotency identity includes **operation kind**, but lookup accepts only a key and may return either proposal or decision state. The same principal can legally reuse a key for both kinds, making recovery after an interrupted reply ambiguous. Either make keys unique across kinds per project/principal or include kind in lookup and specify collision behavior. Add a lost-reply test with both operation types. |
| Blocker | **ARCHITECTURE.md — Retrieval and evidence; contract.d.ts — `RecallResult`** | `G < R` does not by itself establish semantic coverage: a newly added or replaced relevant page can be missed by lexical-tail search for a paraphrase. The design says not to claim *full* freshness, but `hybrid-with-lexical-tail` and its coverage rules do not explicitly disclose that semantic search excludes pending revisions, including when the tail is within budget. Define coverage as indexed semantic scope plus lexical tail—not recall completeness—and require abstention/no absence inference for this case. Test a stale-generation paraphrase miss. |
| Material | **ARCHITECTURE.md — Retrieval and evidence; Database authority** | Hit revalidation is specified, but the one-hop expansion does not explicitly require project authorization and snapshot-consistent page-head/active-state validation for every expanded target. Compound foreign keys alone do not define traversal or prevent an old link from presenting a superseded page as current. Specify those checks for expansion and distinguish historical evidence from current pages; add cross-project and retired/superseded link tests. |
| Material | **contract.d.ts — `ProposalSnapshot`; ARCHITECTURE.md — Proposal and publication state machine** | `ProposalSnapshot.state` can be a `ProposalReceipt`, which is an operation receipt owned by the proposer, while the separate curator must inspect the proposal. This conflates proposal state with principal-scoped operation state and leaves unclear whether receipt/key disclosure is intended. Define a separate proposal-state union without another principal’s operation key; retain principal-scoped receipt lookup. |
| Material | **ARCHITECTURE.md — Usage; contract.d.ts — `Knowledge.recall`** | The usage example implies degraded coverage may be returned by a default recall, while the contract defaults to `require-hybrid-current`. Align the example and policy: explicitly request `allow-degraded` where the agent is expected to inspect degraded results, and document the default `not-ready` path. |
